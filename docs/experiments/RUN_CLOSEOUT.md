# 实验结束后的固定更新规范

生效：2026-09-26。与根目录[AGENTS.md](../../AGENTS.md)配套；本页规定每次运行结束后按什么条件更新哪些文件，不靠聊天记忆。用户授权范围和AGENTS的正式运行规则优先；本页不新增训练/Test授权。

## 1. 谁负责、何时完成

用户执行正式命令；agent核查用户返回的既有产物、记录结果并提交。单纯“跑完了”不是通过证明，先核查本次声明的状态和验收项。失败、部分完成及有效低结果同样交接。声明了串行批次时，可在一个批次审计中逐臂记录，不要求每个seed复制一篇长文。

**声明阶段就写明`记录更新目标`**；结束后按该清单完成。缺少旧声明清单时，从当前日志和实验族定位本次相关文件，先在审计记录列明补定目标，再执行；不猜测、不批量修改所有历史文档。

## 2. 文件与触发条件

| 类别 | 文件 | 何时更新 / 怎么更新 |
|---|---|---|
| 每次必做 | `TRAINING_LOG.md` | 保留pending原文，追加completed/failed或如实描述部分结果；当前状态/交接摘要若变化同步更新。详细表格放审计，日志留结论、协议、来源和链接 |
| 每次必做 | 本次指定的`docs/research/<实验族>_AUDIT_<日期或版本>.md` | 记录每臂身份、命令/参数delta、选模/指标、Test chronology、验收、指纹、意义/限制、唯一下一步。简单诊断可在既有适当审计文件追加新节；不重写旧结果 |
| 每次检查，状态/证据入口变化则更新 | `docs/experiments/README.md` | 更新相关实验族的一行及最新审计链接；无变化注明“已核对，无需修改” |
| 每次检查，相关格子变化则更新 | 当前活跃结果矩阵（见第3节） | 更新本次对应格子状态和审计链接。有效低值算完成，失败留失败原因；不得把Val填进Test格子 |
| 新文件/运行记录/资产大小变化时生成 | `tools/build_experiment_navigation.py`的输出 | 在所有人工编辑完成后刷新一次，见第4节；不手工修生成表 |
| 当前阶段/入口变化才更新 | 根`README.md`、`docs/README.md` | 根总览只改短状态/链接，不复制每个seed的指标；链接稳定且摘要无变化时无需编辑 |
| 论文结论/覆盖范围变化才更新 | 当前正文稿、论文缺口表 | 仅同步实际受影响主张，附审计来源；新实验完成不自动重写所有稿件 |
| 政策/启动流程确实变化才更新 | `AGENTS.md`、本页 | 需事前pending和事后记录。普通完成运行不编辑政策 |
| 协议参数或实现改变时 | 源码、profile、环境/协议文档 | 必须按原before/after规则独立声明变化；不能在结果审计中悄悄调参 |
| 仅经授权归档/结果冻结时 | `archive/training/`完整快照、标签、standalone bundle、物理备份 | 普通完成运行不创建新快照/标签、不压缩历史；正式里程碑按AGENTS另执行，忽略资产须真实备份 |
| 保持原样 | 旧声明/历史审计、原manifest、checkpoint、曲线/原始日志 | 不改资格标记、不删除失败/低结果；修正解释用新条目，新评价用独立报告，旧证据仍可追溯 |

“每次检查”不意味着每次必须制造文件差异。允许清单标记`无变化/不适用 + 原因`，禁止为了交接而复制整套历史。

## 4. 生成目录的固定做法

元数据维护命令（从仓库根目录执行，不启动实验）：

```powershell
& 'D:\miniconda\envs\run_5060\python.exe' -B tools/build_experiment_navigation.py
```

当前生成输出共6个：`docs/experiments/FILES.md`、`docs/experiments/RUN_RECORDS.md`、`archive/training/ENTRY_INDEX_2026-09-26.md`、`archive/catalog/README.md`、`archive/catalog/WORKSPACE_FILES_2026-09-26.jsonl`、`archive/catalog/RUN_RECORDS_2026-09-26.jsonl`。名称中的日期是现行目录版本，不是每次生成日期；这些导航可刷新，完整历史快照不可重写。声明或审计记录实际刷新日期/对应阶段。

工具只读文件元数据、exp JSON及历史文字来建索引；不加载数据矩阵/模型，不做新验收。它不会替你更新科学结论。资产目录有明确排除项，不能当备份或完整历史运行计数。

## 5. 收尾顺序与提交门槛

1. 读取本次pending/声明及记录目标，检查Git状态；只读核查实际产物、参数delta、选择/测试身份及声明验收。不可为审计而重新训练/排名；需要新执行时另申请。
2. 写审计，再追加日志outcome；结果有效但差时写completed并收缩结论。执行/硬验收失败才写failed，缺少证据时写清尚未审结，不伪造成功或退出码。
3. 按第2–3节更新活跃导航/矩阵及触发的正文；列清已更新、无变化、不适用项目。旧记录原文保留。
4. 所有人工文件完成后刷新目录；检查相关本地链接、差异/空白、清单覆盖，以及“哪次Test、哪个所选checkpoint”没有混淆。稳定大资产不为无关文档修改反复全量哈希。
5. 暂存本次范围并创建一个本地结果提交；不提交忽略产物或无关用户文件。结果交接报告分支、提交、工作区状态、审计入口、有效结论/限制和唯一下一步。提交hash放最终交接；下次正式声明引用它，不为把提交hash写入自身而追加循环提交。

结束记录可用短表：`目标文件 | 已更新/无变化/不适用 | 原因或链接`。正式运行的必要指标、Test次数/时间顺序、所选与被测checkpoint相等证据及身份仍按AGENTS完整记录；本页不能替代这些验收内容。
